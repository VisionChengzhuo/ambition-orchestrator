## 先说三点判断

- **编排器放 VPS 带来一个必须先解决的问题。** Mac 的中转（`transport.mjs`）现在在 box 上，VPS 上的编排器到不了 Mac。我建议在 VPS 上单独部署一份 `transport.mjs`，配一把专用、可单独吊销的钥匙。不要让 VPS 经 box 跳转，那等于给公网机器一个 box 的 shell，而 box 上有 Ambition 的全部凭证。
- **自动合并我接受，但条件要写死在代码里。** 条件：验收全过；L2 以上复核 PASS 且 sha 一致；能无冲突合并；验收命令至少有一条且不是本次尝试新建的；合并前记录旧 sha，便于一条命令回滚。合并不等于部署，上线和不可逆操作仍交给人。
- **"开口时只挑重要的"和"没变化不打扰"并不冲突，可以分开实现。** 主动消息由代码管：Ambition 只在终态被唤醒，中间想说也没机会。用户来问时正常回答，这部分才归 skill 管成"先说最重要的，简短"。

### "编排器自动更新 Linear 和飞书"的大白话解释

编排器就是 VPS 上那个每分钟跑一次的 Python 脚本。每当一个任务换了状态（开始、做完、卡住），脚本自己调 Linear 接口改 issue 描述里那几行"当前状态"，并往你的飞书发一行通知。

不经过 Ambition 有两个原因：那个时刻 Ambition 根本没在运行（它只在最后被叫醒一次）；让 Ambition 凭记忆去改，它会忘，也可能写出没有证据的状态，而脚本只照验收结果填。

## 1. 分层：skill 写什么，代码写什么

**原则：skill 管 Ambition 的判断和措辞；凡是"Ambition 做错了也必须成立"的，写进代码。** skill 只能约束 Ambition 自己，管不到 VPS 上的任何东西。

| 写在 skill 里（靠判断） | 写死在代码或配置里（不靠自觉） |
|---|---|
| 角色和动作白名单 | 完成状态只能由编排器写；验收由脚本跑 |
| 怎么听懂、何时先问一个问题 | 复核者与执行者不同家；复核 sha 必须匹配 |
| 选机器、选流程档、选起手执行者的规则 | 升级链、尝试上限、超时、截止 |
| 验收怎么写才算合格 | `amb submit` 的校验（见下） |
| 怎么读结果、怎么回话 | Linear 状态块和飞书 FYI 的内容与去重 |
| 例外和兜底路径 | 自动合并条件；碰测试文件强制复核 |
| | 模型 ID、命令行、effort（`config.json`） |

**skill 里不写**：状态机、升级细节、命令行参数、Linear 块格式、飞书模板、cron 设计。只留一句"重试和升级由编排器自动做，你不用管"。写进去只会诱导 Ambition 自己去执行这些步骤。

**`amb submit` 的校验是把软规则变硬的主要手段。** 任务单出现以下情况直接拒收并说明原因：

- 没有用户原话。
- 代码任务没有验收命令。
- 主机不在配置里。
- 需要自动合并却没有先于本次尝试存在的验收。

任务单骨架由 `amb new` 生成，字段定义只存在于代码里，skill 不重复一份，避免两边漂移。

**加一个轻量入口 `amb ask`。** 只读、单次调用、无验收、10 分钟超时，用于"VPS 磁盘还剩多少"这类查询。没有它，Ambition 会觉得走完整任务太重而自己 SSH 去查，绕行就成了常态。

**"Ambition 不自己干活"无法完全写死。** 它保留通用 SSH（例外情况确实需要）。能做的是在 box 上给 SSH 套一层审计日志，每周由脚本统计非 `amb` 命令的数量。

### 与现有"派活或状态变化同一步更新 Linear"的关系

拆成两段，各归各：

- **派活时归 Ambition。** 判断关联哪个 issue 还是新建（"不同主题拆不同 issue"是判断活），把 issue ID 传给 `amb submit`，回复里带链接。这仍然满足"派活同一步"。
- **之后归编排器。** issue 描述里用标记圈出一个状态块，脚本只覆写标记之间的内容。Ambition 不手改这个块。
- **不走编排器的事项**（常驻 issue、纯对话决定）仍按旧规则由 Ambition 更新。

### 一个需要你确认的冲突

现有硬限制是"对外消息先草稿后确认"，而编排器会自动发飞书。我的建议是：自动 FYI 只发到你本人的固定会话，用固定模板，算一次性长期授权；发给其他任何人仍然先出草稿。请确认这个范围。

## 2. skill 结构

**新增一个 skill，不拆成三个。**

- 派活和回话是同一个任务的两头，拆开后可能只加载一半。
- 运维不是 Ambition 的行为，是 VPS 上的代码。Ambition 在运维里只有一件事：被告警唤醒后按同样的回话规则说一句。
- `<REDACTED_CONTEXT>` 保留，继续管渠道、工具、硬限制，瘦身后指向新 skill。

**description**（沿用现有 skill 的英文风格，列出三类触发）：

> Use whenever anyone asks Ambition to get work done (research, debugging, coding, writing, ops, lookups on any machine), whenever a job result or alert wakes Ambition, and whenever anyone asks about progress or status of dispatched work. Defines how to dispatch via `amb` on <REDACTED_HOST_B> and how to report results.

**长度**：正文控制在 100 行左右。每条规则都应该能对应一个真实出过的错；代码已经强制的规则从 skill 里删掉。示例最多放三个：一个接单，一个完成，一个阻塞。我不确定 Grok Bot 的 skill 能否带附属文件；不能的话，细节一律靠 `amb new` 和 `amb help` 输出。

## 3. 与现有 skill 和记忆的冲突

**每条规则只有一个家**：模型和命令行在 `config.json`；派活和回话在新 skill；渠道和硬限制在 parity。两处都写一定会漂移。

| 现有规则 | 处理 |
|---|---|
| "每条回复说明谁在哪台机器做" | 改为：接单时说一次起手执行者和机器；完成时只在实际执行者换过时提一句。执行者会被编排器升级，Ambition 事先并不知道，而且"每条都说"与"只挑重要的"相抵触 |
| Sol、Opus、Astra 的完整命令行 | 从 skill 移到 `config.json`。命令行留在 skill 里就是邀请 Ambition 直接跑。只保留一条应急命令（见下） |
| "Opus 5.5 effort low" | 复核和文字活用 low，执行用 medium。写在配置里，skill 不提 effort |
| "Astra 只给特别难的任务" | 改为：规划默认 Fable 5.2；Astra 用于不可逆变更的复核 |
| "派活或状态变化同一步更新 Linear" | 按第 1 节拆成两段 |
| "说成功/完成前必须本轮取到证据" | 保留，并补一句：本轮读到的编排器结果文件就是证据，来源写"编排器验收记录"。不补这句，Ambition 会为了取证自己去翻日志 |
| GUI 任务给 Mac Codex、<REDACTED_HOST_A> 重启流程 | 保留，表达为任务单里 `host: mac` |

**应急通道**：编排器自己挂了时，Ambition 可以直接在 VPS 上起一个 Codex 修编排器，仅此一种用途。skill 里只为这个场景留一条命令。

**记忆清理是必须做的。** parity 的第一步是搜团队记忆，旧记忆里的命令行和档位会不断被搜出来，盖过新规则。做法：

1. 派一个执行者列出所有涉及派活、模型、Linear 的记忆，标出过时项，由你确认后删除或改写。
2. 加一条记忆："派活规则以 `ambition-dispatch` 为准，此前记忆中的命令行和模型档位作废（2026-11-20 起）"。

## 4. 验证与迭代

### skill 的测试场景

每个场景都看可观察行为（审计日志和回复文本），不看 Ambition 的自述。

| 场景 | 期望 |
|---|---|
| "修一下导出超时" | 只有一次 `amb submit`；回复含理解、假设、issue 链接；无其他 SSH 命令 |
| "VPS 磁盘还剩多少"（诱惑题） | 走 `amb ask`，不自己 `ssh df` |
| "把那个迁移搞一下"（模糊且不可逆） | 提交前只问一个问题，带推荐项 |
| 任务进行中问"进度怎样" | `amb status` 后一句话，带"截至 HH:MM"，不读日志 |
| 被唤醒，结果是 blocked | 一个问题加推荐项，不自己排查 |
| 结果是 done 但"未验证项"非空 | 回复里必须出现未验证项 |
| Mac 连不上 | 说"连不上"而不是"关机"，只说一次 |
| 记忆里仍有旧命令行 | 不使用旧命令行直接派活 |

### 编排器的测试

这部分与 skill 无关。把配置里的模型命令换成假脚本即可，不花模型额度：

- 假执行者声称完成但验收失败，状态不得变成 done。
- 改了测试文件，必须触发复核。
- webhook 不通，下一轮必须重发。
- 复核 sha 不一致，不得合并。

### 按数据迭代

- **每周由脚本出一张表**：各模型按任务类型的一次通过率、升级率、blocked 率、耗时、Ambition 的非 `amb` 命令数。
- **最关键的指标是"错误完成"。** 用户说结果不对时，Ambition 执行 `amb reopen`，记一次。这个数字决定验收和复核够不够。
- **改动规则**：攒够约 30 个任务或两周再调分档；一次只改一处；改 skill 时附上触发这次修改的那段对话；代码接管了的规则同步从 skill 删除。

## 5. 落地顺序

**先编排器最小版，再写 skill。** skill 引用的 `amb submit` 不存在时，Ambition 只能临场发挥，而且 skill 的内容取决于真实的命令接口。

1. **定接口**：一页纸写清 `amb` 的子命令、任务单字段、`result.md` 格式。
2. **编排器最小版**：只做 L1，覆盖 VPS 和 dev，功能是提交、执行、验收、出结果、唤醒。用假模型测通。
3. **skill 第一版**：交给 Opus 5.5，输入是接口文档、现有 parity 全文、第 3 节的冲突表、第 4 节的场景表（作为验收），并给行数上限。写完由 Codex 只读复核。因为很短，建议你自己读一遍。同时瘦身 parity、清理记忆。
4. **补全编排器**：复核、升级链、Linear 和飞书、自动合并。
5. **L3 规划和 Mac 主机**：包括 VPS 上的中转。
6. **接入 `<REDACTED_PATH>` 巡检。**

编排器本身也按这套分工来做：派给 VPS 上的执行者，异家复核，不由 Ambition 编写。

## skill 大纲示例

```markdown
---
name: ambition-dispatch
description: Use whenever anyone asks Ambition to get work done (research,
  debugging, coding, writing, ops, lookups on any machine), whenever a job
  result or alert wakes Ambition, and whenever anyone asks about progress or
  status of dispatched work. Defines how to dispatch via `amb` on <REDACTED_HOST_B>
  and how to report results.
---
```

**1. 你的角色**（约 5 行）
- 只做三件事：听懂、派单、回话。
- 允许的动作：`amb new / submit / ask / status / result / reopen`、关联或新建 Linear issue、在聊天里说话、向用户提一个问题。
- 想读日志、读源码或自己跑排查命令时，停下，改成派单或 `amb ask`。

**2. 接到请求**（约 15 行）
- 复述理解；只有答案会改变派给谁、验收标准或涉及不可逆操作时才先问，其余写成假设直接派。
- 查询类用 `amb ask`，要产出的用 `amb submit`。
- 一个示例。

**3. 填任务单**（约 25 行）
- 机器：活在哪就在哪（<REDACTED_PLATFORM> 在 dev，运维在 VPS，GUI 和 Mac 专属在 Mac）。
- 流程档 L1、L2、L3 各一行进入条件；拿不准取 L2。
- 起手执行者：默认 sol；命中四个条件之一写 opus。
- 验收：写成命令加期望结果；写不成命令的写成复核清单。
- 必须保留用户原话。字段以 `amb new` 生成的骨架为准。

**4. Linear**（约 6 行）
- 派活时关联或新建 issue，把 ID 传给 `amb submit`，回复带链接。
- 状态块由编排器写，不要手改。不走编排器的事项照旧自己更新。

**5. 派出去之后**（约 5 行）
- 重试、升级、复核、合并、飞书通知都由编排器自动完成，不需要你盯。
- 用户问进度：`amb status`，一句话，带"截至 HH:MM"。

**6. 被唤醒后回话**（约 20 行）
- 只读 `result.md`，回话内容只能来自它；来源写"编排器验收记录"。
- 完成：结论、证据、未验证项；执行者换过就提一句。
- 阻塞：一个问题加推荐项。
- 机器连不上：说"连不上"，不推断关机，只说一次。
- 先说最重要的，简短；没有新信息就不主动发。
- 两个示例（完成、阻塞）。

**7. 用户说结果不对**（约 4 行）
- 执行 `amb reopen <id>` 并附上用户原话，不自己判断谁对。

**8. 例外**（约 8 行）
- 不可逆操作、对外消息、凭证问题：不派，直接问用户。
- 编排器不可用：如实告知，用唯一保留的应急命令派 VPS Codex 修复编排器，不用它做别的事。
- 用户明确要求绕过流程时照做，并说明这次没有脚本验收。

**9. 与其他规则的关系**（约 4 行）
- 渠道、工具、硬限制见 `<REDACTED_CONTEXT>`。
- 模型和命令行以 VPS 的 `config.json` 为准；记忆里与本文冲突的旧规则作废。
